Service-Layer

NvmApiService – handleError entfernen XS ✓ erledigt nvm-api.service.ts
Obwohl der NvmApiService im Frontend (apps/web) liegt, ist er die einzige Kommunikationsschicht zum Backend. Änderungen hier wirken sich direkt auf das Fehlerverhalten der gesamten API-Kommunikation aus.

Jede HTTP-Methode enthielt eine .pipe(catchError(this.handleError))-Kette. Das führte zu drei Problemen:

  1. Fragiler this-Kontext: Methodenreferenz funktionierte nur zufällig.
  2. Redundanz: Fehlerbehandlung war über alle Service-Methoden verteilt.
  3. Wartbarkeit: Jede Änderung musste an jeder Methode nachgezogen werden.
Vorher
getInstalledVersions() {
  return this.http
    .get<InstalledVersionsResponse>(
      '/api/versions/installed'
    )
    .pipe(catchError(this.handleError));
}

private handleError(
  error: HttpErrorResponse
): Observable<never> {
  const msg = error.error?.error
              ?? error.message;
  return throwError(() => new Error(msg));
}
Nachher
getInstalledVersions() {
  return this.http
    .get<InstalledVersionsResponse>(
      '/api/versions/installed'
    );
  // Interceptor normalisiert Fehler
}

Die Normalisierung übernimmt der zentrale httpErrorInterceptor. Der Service enthält nur noch die fachliche Absicht.

Express-Architektur

createApp()-Factory für Testbarkeit S ✓ erledigt apps/api/src/server.ts

Die Express-App wurde direkt beim Modul-Import gestartet. Das machte Supertest-Tests ohne echten TCP-Port unmöglich.

Vorher
const app = express();
app.use(cors(...));
// ...
app.listen(3789);
Nachher
export function createApp() {
  const app = express();
  app.use(cors(...));
  // ...
  return app;
}

if (process.env['NODE_ENV'] !== 'test') {
  createApp().listen(3789, '127.0.0.1');
}

Supertest kann createApp() direkt einbinden – kein TCP-Port, keine Port-Konflikte, CI-sicher.

Performance-Optimierungen

bash -lc → bash -c XS ✓ erledigt nvm.service.ts

Alle nvm-Shell-Aufrufe nutzten ursprünglich das Login-Shell-Flag -l. Das lädt .bash_profile, .bashrc etc. vollständig – auf manchen Systemen mehrere Sekunden Overhead.

Vorher
execFile('bash', ['-lc',
  `${NVM_HEADER} nvm ${args}`])
Nachher
execFile('bash', ['-c',
  `${NVM_HEADER} nvm ${args}`])
// NVM_HEADER setzt NVM_DIR, HOME
// und sourcet nvm.sh explizit
runNvmLsFast – Dateisystem statt Shell M ✓ erledigt nvm.service.ts

GET /api/versions/installed war zuvor ~20 Sekunden langsam, weil nvm ls eine vollständige Shell-Session startete. Ersetzt durch direktes Dateisystem-Lesen mit node:fs/promises:

Vorher (~20 Sekunden)
async function runNvmLs() {
  // Startet bash, sourcet nvm.sh,
  // ruft nvm ls auf → Shell-Overhead
  return runNvm('ls');
}
Nachher (< 10 ms)
async function runNvmLsFast() {
  const nodeDir = join(NVM_DIR,
    'versions/node');
  const aliasDir = join(NVM_DIR, 'alias');
  // Liest Verzeichnisse direkt aus dem
  // Dateisystem – kein Shell-Prozess
}

Speedup: ~2000× für den häufigsten Endpunkt.
