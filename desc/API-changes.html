Querschnittsänderungen

Fehler-Normalisierung via httpErrorInterceptor Pattern-Änderung ✓ erledigt

Vor dem Interceptor gab es keine garantierte Einheitlichkeit: Jede NvmApiService-Methode wandelte HttpErrorResponse lokal um. Jetzt verarbeitet der zentrale Interceptor alle HTTP-Fehler:

HTTP Response (4xx/5xx)
↓
HttpErrorResponse Angular-intern
↓
httpErrorInterceptor extrahiert err.error?.error ?? err.message
↓
Error({ message }) einheitliches Format für die gesamte App
↓
resource.error() / Template Anzeige im Log-Panel

Das Backend-Fehlerformat {"error": "Fehlermeldung"} wird durch den Interceptor direkt extrahiert. Die Applikation arbeitet immer mit einfachen Error-Objekten, nie mehr mit HttpErrorResponse.

GET-Endpunkte: Von subscribe() zu rxResource() Konsumierungs-Muster ✓ erledigt
EndpunktKonsumiert vonVorherNachher
GET /api/status StatusCardComponent manuelles subscribe() rxResource()
GET /api/versions/available RemoteVersionsCardComponent manuelles subscribe() rxResource()
GET /api/versions/installed NvmStateService manuelles subscribe() rxResource()
GET /api/versions/aliases AliasesCardComponent manuelles subscribe() rxResource()

Mutationen (POST /api/versions/install, DELETE, etc.) bleiben imperativ – sie haben Seiteneffekte, sind nicht idempotent und lösen Reloads aus statt eigene Daten darzustellen.

// Reload nach einer Mutation:
this.installedResource.reload();

// Template-Zugriff:
versionsResource.isLoading()
versionsResource.value()
versionsResource.error()

Neue Endpunkte

GET /api/status Erweiterung ✓ erledigt

Das optionale Feld nvmLatestVersion wurde hinzugefügt:

Vorher
{
  "nvmAvailable": true,
  "nvmVersion": "0.39.7",
  "nodeVersion": "v22.3.0"
}
Nachher
{
  "nvmAvailable": true,
  "nvmVersion": "0.39.7",
  "nodeVersion": "v22.3.0",
  "nvmLatestVersion": "v0.40.1"
}

nvmLatestVersion wird nur geliefert, wenn die GitHub-Releases-API erreichbar ist (5 s Timeout). Das Frontend zeigt bei Unterschied einen „Aktualisieren"-Button.

POST /api/nvm/update Neu ✓ erledigt

Löst ein nvm-Self-Update via git fetch --tags && git checkout <version> im NVM_DIR aus. Nutzt SSE-Streaming (gleiche Mechanik wie POST /api/versions/install).

Request Body:

{ "targetVersion": "v0.40.1" }

Response: SSE-Stream mit progress-Events, abschließend complete oder error.

Frontend-Integration: InstallModalState.action wurde um 'nvm-update' erweitert; alle drei Phasen (running / success / error) zeigen nvm-spezifische Modal-Texte.

POST /api/nvm/open-dir Neu ✓ erledigt

Öffnet NVM_DIR im Dateimanager (open auf macOS, xdg-open auf Linux).

Request: kein Body erforderlich

Response (200):

{ "opened": true }

Sicherheitshinweis: Kein User-Input → kein Injection-Risiko. Der Pfad kommt ausschließlich aus der Server-Konfiguration (NVM_DIR).

LTS-Alias-Endpunkte (Dateisystem-basiert) Neu ✓ erledigt

nvm unterstützt nvm alias lts/<codename> nicht nativ. Die neuen Endpunkte schreiben/löschen Alias-Dateien direkt im Dateisystem (~/.nvm/alias/lts/).

Methode & PfadRequestResponse
POST /api/versions/aliases/lts { "codename": "iron", "version": "20.12.2" } { "success": true }
DELETE /api/versions/aliases/lts/:codename – { "success": true }

Validierung: isValidLtsCodename – Whitelist-Regex /^[a-z]+$/.

POST /api/versions/stable Neu ✓ erledigt

Setzt den stable-Alias auf eine beliebige Version oder LTS-Linie.

// Request
{ "version": "22.3.0" }

// oder LTS-Codename
{ "version": "lts/iron" }

Geänderte Endpunkte

POST /api/versions/use Verhalten geändert ✓ erledigt
Vorher (temporär)
// nvm use X
// Nur für die Child-Prozess-Session
// wirksam – kein persistenter Effekt
Nachher (persistent)
// nvm alias default X
// Schreibt in ~/.nvm/alias/default
// Alle zukünftigen Shells nutzen X

Root Cause: nvm use setzt die Version nur in der aktuellen Shell-Session. Da der Backend-Prozess in einer isolierten Child-Shell läuft, hatte der Befehl keine sichtbare Wirkung.

Eingabevalidierung

Whitelist-Strategie für alle Endpunkte

Alle Endpunkte, die Versions- oder Alias-Namen entgegennehmen, validieren diese vor der Shell-Übergabe:

FunktionRegex / LogikFehler bei Verletzung
isValidVersionInput /^(\d+\.\d+\.\d+|lts\/[a-z]+|[a-z]+|\d+)$/ HTTP 400
isValidAliasName /^[\w.\-/]+$/ HTTP 400
isValidAliasTarget wie isValidVersionInput HTTP 400
isValidLtsCodename /^[a-z]+$/ HTTP 400

Bei Verletzung: { "error": "Invalid ..." } – keine Shell-Ausführung findet statt.
