Schritt 1.2 – provideHttpClient(withFetch()) XS Low Impact ✓ erledigt app.config.ts
Vorher
provideHttpClient()
Nachher
provideHttpClient(withFetch())
💡 Konzept: XMLHttpRequest (XHR) vs. native Fetch API

XMLHttpRequest ist die ursprüngliche Browser-API für HTTP-Anfragen – eingeführt um 2000 für die damals revolutionären AJAX-Techniken. Sie arbeitet über Event-Callbacks und einen Zustandsautomaten (.readyState 0–4). Angular nutzte XHR bislang intern im HttpClient.

Die native Fetch API wurde 2015 als moderner Ersatz standardisiert und ist heute in jedem Browser sowie in Node.js (ab v18) nativ verfügbar. Ihr Kernprinzip:

// Fetch API direkt (ohne Angular)
const response = await fetch('/api/status');  // gibt ein Promise zurück
const data     = await response.json();        // Body-Parsing ebenfalls async
  • Promise-basiert statt callback-gesteuert – direkte async/await-Unterstützung
  • Streams-fähig – Antwort-Body kann als ReadableStream konsumiert werden
  • Abortierbar per AbortController – saubere Ressourcenfreigabe ohne Hacks
  • Standardkonform – identisches Verhalten in Browser und Node.js (SSR)

Warum withFetch() aktivieren?

Angular 17.3 führte withFetch() als optionalen Schalter ein, um Breaking Changes für bestehende Apps zu vermeiden. Seit Angular 19+ ist es die empfohlene Einstellung für neue Projekte.

XHR (Standard)Fetch (mit withFetch())
Bundle-Größe Eigene XhrBackend-Klasse wird mitgebundelt Kein eigenes Backend – nutzt natives fetch()
SSR / Node.js Benötigt externe XHR-Polyfills auf dem Server Kein Polyfill nötig – Node.js 18+ hat fetch nativ
Abbruch Angular verwaltet eigenen Abbruch-Mechanismus Native AbortController-Integration
DevTools Erscheint als xhr im Network-Tab Erscheint als fetch – besser filterbar
Was ändert sich für den Angular-Code? Nichts. Die HttpClient-API bleibt identisch – this.http.get(), this.http.post() etc. funktionieren weiterhin genauso. withFetch() ist ausschließlich ein Implementierungsdetail im Innern von Angular. Der Wechsel ist deshalb risikofrei. 
// app.config.ts – vollständiger Kontext
export const appConfig: ApplicationConfig = {
  providers: [
    provideZonelessChangeDetection(),
    provideHttpClient(withFetch()),   // ← einzige Änderung
    provideRouter(routes),
  ],
};

Schritt 1.5 – ChangeDetectionStrategy.OnPush M High Impact ✓ erledigt
💡 Konzept: Angular Change Detection

Angular muss wissen, wann das DOM aktualisiert werden soll – also wann sich Daten geändert haben. Dafür ist die Change Detection (CD) zuständig. Sie wird nach jedem asynchronen Ereignis ausgelöst: Klick, HTTP-Antwort, Timer, aufgelöstes Promise.

Standardverhalten (Default-Strategie): Angular prüft nach jedem solchen Ereignis alle Components in der gesamten App – von oben nach unten durch den gesamten Component-Tree. Das ist sicher, aber aufwändig.

💡 Konzept: Der Component-Tree

Eine Angular-App ist als Baum von Components aufgebaut. AppComponent ist die Wurzel; sie enthält alle anderen Components als Kinder und Enkel:

AppComponent
├── AppHeaderComponent
├── StatusCardComponent
│   └── CardComponent
│       └── LoadingStateComponent
├── ActionCardComponent
├── InstalledVersionsCardComponent
│   └── CardComponent
├── AliasesCardComponent
├── RemoteVersionsCardComponent
└── LogCardComponent

Mit der Default-Strategie traversiert Angular diesen Baum bei jedem Ereignis vollständig – auch wenn nur der Header neu gerendert werden müsste.

💡 Konzept: Signals und Signal Inputs

Signals sind reaktive Primitive (Angular 16+). Ein Signal ist ein Wrapper um einen Wert, der Angular präzise benachrichtigt, sobald sich dieser Wert ändert. Im Gegensatz zu gewöhnlichen Properties weiß Angular, welches Template welche Signals liest.

const count = signal(0);            // Signal anlegen
count.set(1);                        // Wert setzen → Angular erfährt es sofort
console.log(count());                // Wert lesen (als Funktion aufrufen)

const double = computed(() => count() * 2);  // Abgeleiteter Wert

Signal Inputs (aus Schritt 1.4) sind Signals, die von außen per Property-Binding befüllt werden. Angular kennt dadurch die Abhängigkeit explizit:

readonly versions = input<NvmVersion[]>([]);
// Angular weiß: wenn `versions` sich ändert,
// muss NUR dieses Template neu gerendert werden.

Default vs. OnPush – der Unterschied

Mit Default prüft Angular eine Component bei jedem CD-Zyklus, egal ob sich ihre Daten geändert haben. Das sind die „unnötigen Default-CD-Zyklen": Ein Klick in ActionCardComponent löst einen Zyklus aus, der auch RemoteVersionsCardComponent prüft – obwohl dort nichts passiert ist.

Mit OnPush überspringt Angular eine Component und ihren gesamten Teilbaum, solange keine der folgenden Bedingungen erfüllt ist:

AuslöserErklärung
@Input()-Referenz ändert sichAngular vergleicht per === (shallow, nicht Deep-Equal)
Signal im Template ändert sichAngular kennt die Abhängigkeit exakt → präzises Re-Render
Event im eigenen Templatez.B. (click) innerhalb der Component
async-Pipe emittiertObservable-basierte Patterns
markForCheck() / detectChanges()Programmatischer Auslöser (manuell)

Visuelle Vorstellung: Default vs. OnPush

Default – prüft alles
Ereignis: Klick auf "Installieren"

AppComponent          ✓ prüfen
├── AppHeaderComponent    ✓ prüfen
│   (nichts geändert)
├── StatusCardComponent   ✓ prüfen
│   (nichts geändert)
├── ActionCardComponent   ✓ prüfen
│   (Ereignisquelle)
├── InstalledVersions…    ✓ prüfen
└── AliasesCardComponent  ✓ prüfen
    (nichts geändert)
OnPush + Signals – nur Nötiges
Signal `isLoading` geändert

AppComponent          ✓ Signal gelesen
├── AppHeaderComponent  ⏭ überspringen
│   (kein Signal geändert)
├── StatusCardComponent ⏭ überspringen
│   (kein Signal geändert)
├── ActionCardComponent ✓ Ereignisquelle
├── InstalledVersions…  ✓ Signal gelesen
└── AliasesCardComponent ⏭ überspringen
    (kein Signal geändert)
Warum ist Schritt 1.4 (Signal Inputs) Voraussetzung?
Mit klassischen @Input()-Properties würde OnPush nur bei Referenzänderungen (===) auslösen. Das ist spröde: Wer ein Array mutiert statt es zu ersetzen, sieht keine Aktualisierung. Signal Inputs lösen das elegant – Angular registriert die Abhängigkeit automatisch und triggert präzise beim tatsächlichen Wertewechsel, unabhängig von der Referenz. 
import { ChangeDetectionStrategy, Component } from '@angular/core';

@Component({
  changeDetection: ChangeDetectionStrategy.OnPush,
  // ...
})

Alle 12 Components wurden umgestellt: app.ts, install-modal, app-header, app-footer, status-card, action-card, installed-versions-card, aliases-card, remote-versions-card, log-card, card, loading-state, spinner.

Schritt 1.6 – OnChanges durch effect() ersetzen S Medium Impact ✓ erledigt install-modal.component.ts
💡 Konzept: ngOnChanges und seine Schwächen im Signals-Zeitalter

ngOnChanges ist ein Lifecycle-Hook: Angular ruft ihn auf, sobald sich ein @Input()-Property ändert. Die Component muss dafür OnChanges implementieren und bekommt ein SimpleChanges-Objekt – mit String-Keys ohne Typsicherheit (changes['state']).

Das Problem: Sobald der Hook Ressourcen anlegt (hier: ein setTimeout-Timer), muss dieselbe Component auch OnDestroy implementieren, um aufzuräumen. Das Ergebnis:

  • Zwei Interfaces, die nur gemeinsam Sinn ergeben
  • Anlage-Logik in ngOnChanges, Bereinigung in ngOnDestroy – räumlich getrennt
  • Dupliziertes clearTimeout an zwei Stellen
  • String-Key changes['state'] – keine Compile-Zeit-Sicherheit
💡 Konzept: effect() – reaktive Seiteneffekte mit Signals

effect() läuft einmalig beim Erstellen der Component und danach automatisch erneut, sobald sich ein Signal ändert, das im Effekt gelesen wird – Angular erkennt die Abhängigkeit selbst.

Die Cleanup-Funktion wird per onCleanup() direkt im selben Effekt registriert. Angular führt sie aus, bevor der Effekt erneut auslöst und wenn die Component zerstört wird. ngOnDestroy wird damit überflüssig.

Vorher → Nachher im Detail

Vorher – Logik an zwei Stellen
// Problem: 2 Interfaces, dupliziertes
// clearTimeout, kein Type-Safety
implements OnChanges, OnDestroy {
  @Input() state: InstallModalState = null;
  private autoCloseTimer?: ReturnType<
    typeof setTimeout>;

  ngOnChanges(changes: SimpleChanges) {
    if (changes['state']) {       // String-Key!
      clearTimeout(this.autoCloseTimer);
      if (this.state?.phase === 'success') {
        this.autoCloseTimer = setTimeout(
          () => this.closed.emit(), 3000
        );
      }
    }
  }

  ngOnDestroy() {
    clearTimeout(this.autoCloseTimer); // ← dupliziert
  }
}
Nachher – alles an einem Ort
// Keine Interfaces, typsicher, Cleanup
// direkt neben der Anlage-Logik
readonly state = input<InstallModalState>(null);
readonly closed = output<void>();

constructor() {
  let autoCloseTimer: ReturnType<
    typeof setTimeout> | undefined;

  effect((onCleanup) => {
    clearTimeout(autoCloseTimer);
    if (this.state()?.phase === 'success') {
      autoCloseTimer = setTimeout(
        () => this.closed.emit(), 3000
      );
    }
    onCleanup(          // ← Bereinigung hier
      () => clearTimeout(autoCloseTimer)
    );
  });
}

OnChanges, SimpleChanges und OnDestroy vollständig aus Importen entfernt. Die Component implementiert keine Interfaces mehr.

Schritt 1.7 – God Component auflösen: NvmStateService L High Impact ✓ erledigt services/nvm-state.service.ts
⚠ Anti-Pattern: God Component

Eine God Component (auch „Fat Component") trägt zu viele Verantwortungen und verstößt damit gegen das Single Responsibility Principle (SRP). app.ts hatte vor diesem Schritt drei Aufgaben gleichzeitig:

  1. Layout – das HTML-Gerüst der Seite zusammenstellen
  2. State – alle Signals der App halten (isLoading, installedVersions, …)
  3. Aktionen – alle Benutzerinteraktionen verarbeiten (onInstall, onUse, …)

Folgen: unkontrolliertes Wachstum (~295 Zeilen), hohe Änderungsrisiken und schlechte Testbarkeit – um onInstall() zu testen, musste die gesamte Angular-Component mit DOM hochgefahren werden.

💡 Konzept: Services und Dependency Injection

Ein Service in Angular ist eine einfache TypeScript-Klasse mit @Injectable(). Kein Template, kein DOM – nur Daten und Logik. Angulars Dependency Injection (DI) stellt eine einzige Instanz der gesamten App bereit (Singleton-Pattern).

@Injectable({ providedIn: 'root' })  // eine Instanz für die gesamte App
export class NvmStateService {
  // Zustand und Logik hier – kein Template, kein DOM
}

// In app.ts: Angular liefert die Instanz automatisch
protected readonly state = inject(NvmStateService);

Schritt 1.8 – confirm() durch Inline-Modal ersetzen M Medium Impact ✓ erledigt aliases-card.component.ts
⚠ Problem: window.confirm() in modernen Apps

confirm() ist eine Browser-API aus den frühen Tagen des Webs. Sie zeigt einen nativen OS-Dialog und liefert synchron true oder false zurück. Das klingt praktisch, hat aber vier ernste Nachteile:

  1. Blockiert den UI-Thread: Die gesamte JS-Ausführung hält an, solange der Dialog offen ist. Kein Spinner, keine Animation, keine Netzwerk-Requests – die App „friert" ein.
  2. Nicht gestaltbar: Das Aussehen bestimmt ausschließlich das Betriebssystem. Schriftart, Farben, Layout lassen sich nicht anpassen – der Dialog passt nie ins App-Design.
  3. Unzuverlässig: Auf mobilen Geräten sieht er anders aus. In iframes und PWAs kann er stumm false zurückliefern. Chrome unterdrückt wiederholte Aufrufe automatisch.
  4. Nicht testbar: Unit-Tests müssen window.confirm manuell überschreiben (spyOn(window, 'confirm')) – fragil und aufwändig.

Die Signal-gesteuerte Alternative

Statt den Lösch-Auftrag sofort auszuführen, speichert ein Signal den „ausstehenden" Alias-Namen. Das Template reagiert und zeigt kontextuell – direkt beim betroffenen Eintrag – eine Bestätigung an:

Vorher
deleteAlias(name: string) {
  // Blockiert UI-Thread, nicht testbar,
  // sieht auf jedem Gerät anders aus
  if (!confirm(
    `Alias '${name}' wirklich löschen?`
  )) return;

  this.api.deleteAlias(name)
    .subscribe(...);
}
Nachher
confirmPendingAlias =
  signal<string | null>(null);

deleteAlias(name: string) {
  this.confirmPendingAlias.set(name);
}
confirmDelete() {
  const name = this.confirmPendingAlias();
  if (name) this.api.deleteAlias(name)
              .subscribe(...);
  this.confirmPendingAlias.set(null);
}
cancelDelete() {
  this.confirmPendingAlias.set(null);
}
<!-- Template: erscheint direkt beim betroffenen Alias -->
@if (confirmPendingAlias() === alias.name) {
  <div role="alert">
    Alias '{{ alias.name }}' wirklich löschen?
    <button (click)="confirmDelete()">Ja, löschen</button>
    <button (click)="cancelDelete()">Abbrechen</button>
  </div>
}

Schritt 1.9 – Zoneless Change Detection XL Low Impact (kurzfristig) ✓ erledigt app.config.ts
💡 Konzept: Was ist Zone.js – und warum wurde es eingeführt?

Angular muss wissen, wann asynchrone Operationen abgeschlossen sind, um Change Detection auszulösen. Zone.js löste das historisch durch Monkey-Patching: Beim App-Start überschreibt es nahezu alle asynchronen Browser-APIs mit eigenen Wrapper-Versionen:

setTimeout      → Zone.js-Wrapper
fetch           → Zone.js-Wrapper
Promise         → Zone.js-Wrapper
addEventListener → Zone.js-Wrapper
XMLHttpRequest  → Zone.js-Wrapper

Wenn eine Operation abschließt, benachrichtigt Zone.js Angular: „Jetzt Change Detection auslösen." Angular prüft dann den gesamten Component-Tree.

⚠ Die Kosten von Zone.js
  • Bundle-Größe: ~35 KB extra (gzipped)
  • Monkey-Patching: Überschreiben von Browser-APIs ist konzeptionell fragil und erschwert Debugging
  • Unvorhersagbarkeit: CD kann zu unerwarteten Zeitpunkten ausgelöst werden
  • Verwirrende Stack-Traces: Zone.js-Wrapper-Frames erscheinen im Debugger
  • SSR / Node.js: Zone.js benötigt auch auf dem Server einen Patch
💡 Konzept: Signals ersetzen Zone.js vollständig

Mit Signal-basiertem State-Management weiß Angular präzise, welche Signals von welchen Templates gelesen werden. Ändert sich ein Signal, löst Angular nur die betroffenen Components aus:

Mit Zone.js
async-Event
  → Zone.js fängt ab
  → Angular: „Check alle
    Components im Tree"
Zoneless + Signals
signal.set(neuerWert)
  → Angular: „Check nur
    Components, die dieses
    Signal lesen"
Warum XL-Aufwand – und trotzdem trivial hier?
XL gilt für eine Migration einer bestehenden Zone.js-App: jede Component auf implizite Abhängigkeiten prüfen, Polyfills entfernen, Tests anpassen. In diesem Projekt war der Schritt trivial: zone.js war nie eingetragen, alle Components nutzten bereits Signal Inputs und OnPush. Die Aktivierung war eine einzige Konfigurationszeile. 
export const appConfig: ApplicationConfig = {
  providers: [
    provideZonelessChangeDetection(),  // Angular 21: stabile API
    provideHttpClient(withFetch()),
    provideRouter(routes),
  ],
};

Schritt 2.1 – ESLint + angular-eslint (Flat Config) M High Impact ✓ erledigt apps/web/eslint.config.mjs
💡 Konzept: Linting – mehr als nur Typen

Der TypeScript-Compiler prüft ausschließlich Typen. Ein Linter analysiert Code nach konfigurierbaren Regeln, die weit darüber hinausgehen:

RegelWas wird erkannt
prefer-on-push-component-change-detectionComponents ohne OnPush
prefer-standaloneComponents, die noch NgModule verwenden
component-selectorFalsches Selektor-Präfix (app-)
templateAccessibilityFehlende alt-Attribute, falsche ARIA-Rollen
💡 Konzept: ESLint Flat Config (ESLint 9+)

ESLint 9 ersetzte die Legacy-Config (eslintrc.json) durch die Flat Config (eslint.config.mjs): eine einzige JavaScript-Datei, die alle Regeln als Array exportiert – expliziter, besser typisierbar, einfacher zu debuggen.

// eslint.config.mjs (vereinfacht)
export default [
  { files: ['**/*.ts'],   rules: { /* TypeScript-Regeln */ } },
  { files: ['**/*.html'], rules: { /* Template-Regeln  */ } },
];

Die wichtigste Konsequenz

Die Regel prefer-on-push-component-change-detection erzwingt zukünftig, was in Schritt 1.5 manuell migriert wurde. Keine neue Component kann mehr ohne OnPush in den Build kommen – der CI-Build schlägt fehl. --max-warnings 0: Auch Warnungen gelten als Fehler.

Nach initialer Bereinigung (fehlende OnPush an Test-Host-Components, ungenutzte Konstante): 0 Lint-Fehler.

Schritt 2.2 – Datenabruf auf rxResource() umstellen L High Impact ✓ erledigt
⚠ Problem: Manueller subscribe()-Boilerplate

HTTP-GET-Aufrufe haben immer drei Zustände: Laden, Erfolg, Fehler. Bei manuellem subscribe() muss dieser Automat jedes Mal von Hand gebaut werden – mit eigenen Signals, eigenem Reset nach Reload und oft vergessenen Randfällen.

  • Redundanz: Jede ladende Component schreibt denselben Boilerplate
  • Randfälle vergessen: error-Signal nach erneutem Laden nicht zurückgesetzt
  • Kein Reload: Nach einer Mutation muss ngOnInit erneut aufgerufen werden
💡 Konzept: rxResource() – deklarativer Lade-Zustandsautomat

rxResource() kapselt den kompletten Lade-Zustandsautomaten in einer Signal-Abstraktion mit vier klaren Slots:

ZustandSignal-MethodeBedeutung
idleresource.status()Noch nicht geladen
loadingresource.isLoading()Request läuft
resolvedresource.value()Daten erfolgreich geladen
errorresource.error()Fehler aufgetreten

resource.reload() löst den Loader nach einer Mutation erneut aus – eine Zeile statt eines ganzen Reload-Mechanismus.

Vorher – Boilerplate in jeder Component
loading = signal(false);
error   = signal<string | null>(null);
data    = signal<NvmVersion[]>([]);

ngOnInit() {
  this.loading.set(true);
  this.api.getRemoteVersions()
    .subscribe({
      next: v => {
        this.data.set(v);
        this.loading.set(false);
      },
      error: e => {
        this.error.set(e.message);
        this.loading.set(false);
      }
    });
}
// Reload: loadData() nochmals aufrufen
Nachher – deklarativ mit rxResource()
protected readonly resource =
  rxResource({
    loader: () =>
      this.api.getRemoteVersions()
  });

// Template:
// @if (resource.isLoading()) { … }
// @if (resource.error()) { … }
// @for (v of resource.value()?.versions
//       ; track v.version) { … }

// Reload nach Mutation:
// this.resource.reload();

Betroffen: status-card, remote-versions-card, nvm-state.service, aliases-card. 185 Tests grün nach Migration.

Schritt 2.3 – action-card: effect() → linkedSignal() S Medium Impact ✓ erledigt action-card.component.ts
💡 Konzept: „Abgeleiteter, aber überschreibbarer Zustand"

Das Versions-Eingabefeld soll sich automatisch befüllen, wenn per prefillVersion-Input eine Version kommt – aber der Nutzer soll ihn manuell überschreiben können. Ein klassisches Spannungsfeld:

  • Abgeleitet: sollte bei neuem prefillVersion automatisch aktualisieren
  • Überschreibbar: darf manuelle Eingabe nicht bei jedem Render überschreiben

effect() ist dafür das falsche Werkzeug – Angular warnt ausdrücklich davor, in einem Effekt in ein anderes Signal zu schreiben. linkedSignal() (Angular 19+) ist genau für dieses Muster gebaut: Quelle + Berechnungsfunktion mit Zugriff auf den vorherigen Wert (prev).

Vorher – effect() als State-Ableitung
versionInput = signal('22');
constructor() {
  effect(() => {
    // Überschreibt auch manuelle
    // Eingabe des Nutzers!
    this.versionInput.set(
      this.prefillVersion() || '22'
    );
  });
}
Nachher – linkedSignal()
protected readonly versionInput =
  linkedSignal({
    source: this.prefillVersion,
    // prev?.value = vorheriger Wert
    // (manuelle Eingabe bleibt!)
    computation: (v, prev) =>
      v || prev?.value || '22'
  });
// Kein Konstruktor, kein effect()
Verhalten: Klick auf „Verwenden" bei v22.3.0 → versionInput = '22.3.0'. Nutzer tippt manuell '20' → Eingabe bleibt. Klick auf v18.0.0 → versionInput = '18.0.0' (neue Source überschreibt wieder).
Schritt 2.4 – Zentrales Error-Handling M Medium Impact ✓ erledigt core/http-error.interceptor.ts
💡 Konzept: HTTP-Interceptoren – Middleware für den HttpClient

Ein Interceptor fängt jeden HTTP-Request und jede Response ab, bevor sie die Anwendungslogik erreicht – identisch zu Middleware in Express. In Angular sind Interceptoren seit v15 funktional (einfache Funktion, kein implements):

HttpClient.get('/api/…')
  ↓ [ Interceptor: Auth-Header ]
  ↓ [ Interceptor: Error-Normalisierung ] ← unser httpErrorInterceptor
  ↓ Backend-Server
  ↑ [ Interceptor: Error-Normalisierung ] ← fängt Fehler-Responses ab
  ↑ [ Interceptor: Auth-Header ]
  ↑ Component / Resource

Die zwei Schutzschichten

// Schicht 1: HTTP-Fehler normalisieren (4xx, 5xx)
// HttpErrorResponse → Error (einheitliches Format für die gesamte App)
export const httpErrorInterceptor: HttpInterceptorFn = (req, next) =>
  next(req).pipe(
    catchError((err: HttpErrorResponse) => {
      const message = err.error?.error ?? err.message;
      return throwError(() => new Error(message));
    })
  );

// Schicht 2: Safety-Net für alle anderen Fehler
// (nicht abgefangene Exceptions, Template-Rendering-Fehler)
@Injectable()
export class GlobalErrorHandler implements ErrorHandler {
  handleError(error: unknown): void {
    console.error('[GlobalErrorHandler]', error);
    // In Produktion: an Monitoring senden (z.B. Sentry)
  }
}

Schritt 2.5 – handleError aus NvmApiService entfernen XS Low Impact ✓ erledigt nvm-api.service.ts

Direkte Konsequenz aus Schritt 2.4: Das fragile catchError(this.handleError) als Methodenreferenz entfällt ersatzlos.

💡 Konzept: Das this-Binding-Problem

In JavaScript hängt this davon ab, wie eine Funktion aufgerufen wird. Als Methodenreferenz (catchError(this.handleError)) verliert sie ihren Kontext – funktionierte hier nur zufällig, weil this in handleError nicht genutzt wurde. Korrekt wäre catchError((e) => this.handleError(e)) – mit dem Interceptor entfällt die Frage vollständig.

Vorher – fragile Methodenreferenz
getInstalledVersions() {
  return this.http
    .get<InstalledVersionsResponse>(
      '/api/versions/installed'
    )
    .pipe(catchError(this.handleError));
    //   ↑ this-Binding fragil!
}

private handleError(
  error: HttpErrorResponse
): Observable<never> { … }
Nachher – reiner HTTP-Aufruf
getInstalledVersions() {
  return this.http
    .get<InstalledVersionsResponse>(
      '/api/versions/installed'
    );
  // Interceptor übernimmt Fehler
  // handleError: gelöscht
}
Schritt 2.6 – Accessibility M Medium Impact ✓ erledigt
💡 Konzept: Accessibility (a11y) – ARIA und Tastaturnavigation

ARIA-Attribute teilen Browser und Screenreadern die semantische Rolle eines Elements mit – unabhängig von seinem visuellen Aussehen. Live Regions benachrichtigen Screenreader automatisch, wenn sich Inhalt dynamisch ändert. Fokus-Management stellt sicher, dass Tastaturnutzer in Modals nicht im Hintergrund navigieren können.

ARIA-AttributBedeutung
role="dialog"Screenreader erkennt Modal-Kontext
aria-modal="true"Hintergrund ist für Screenreader nicht navigierbar
aria-labelledbyVerknüpft Titel mit dem Dialog
aria-live="polite"Neue Inhalte werden beim nächsten Pause vorgelesen
role="alert"Sofortige Screenreader-Ansage (assertive live region)

Umgesetzte Maßnahmen

  effect(() => {
    if (this.state()) {
      this.previousFocus = document.activeElement as HTMLElement;
